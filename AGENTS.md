# Лампада — инструкции для AI-агентов

## Цель и приоритеты

«Лампада» — Flutter-приложение для короткой ежедневной православной сессии:
одна карточка контента на весь экран, без дашбордов и лент. Основной язык
пользовательского интерфейса, комментариев и документации — русский.

iOS — первый приоритет, но Android — поддерживаемая платформа: не допускайте
регрессий в Android release-сборке.

Перед изменением изучите ближайший код и тесты. Полное описание продукта,
архитектуры и известных ловушек находится в `README.md`; этот файл задаёт
обязательные правила выполнения изменений.

## Рабочий цикл

1. Сохраните и не отменяйте чужие незакоммиченные изменения.
2. Вносите минимально необходимое изменение в существующем стиле.
3. Сначала тест, потом код. Для новой доменной логики или багфикса напишите
   падающий тест, убедитесь, что он падает по ожидаемой причине, и только
   потом правьте реализацию. Исключение — правки, которые тестом не
   выражаются (нативные настройки, ассеты, документация).
4. После изменения Dart-кода выполните:

   ```sh
   dart format .
   flutter analyze
   flutter test
   ```

   `flutter analyze` должен давать **ноль** issues, `flutter test` — ноль
   упавших тестов. Ненулевой результат — незавершённая работа, а не
   «известная особенность»; либо починьте, либо явно назовите проблему в
   итоговом сообщении.
5. После изменения `freezed`-entity или DTO с JSON сначала выполните
   кодогенерацию, затем шаг 4:

   ```sh
   dart run build_runner build --delete-conflicting-outputs
   ```

   Не редактируйте вручную файлы `*.freezed.dart` и `*.g.dart`.

Перед передачей результата выполните `git diff --check` и сообщите, какие
проверки действительно были выполнены. Не пишите «проверено», если команда не
запускалась.

## Что проверяет пользователь, а не агент

Приложение запускает только пользователь. Не выполняйте `flutter run`, не
поднимайте симулятор или эмулятор, не собирайте release-артефакты для
визуальной проверки.

Когда изменение затрагивает Android/iOS-код, сборочные настройки, разрешения,
splash-экран или иконки, unit-тесты его не покрывают. В таком случае в итоговом
сообщении отдельным пунктом укажите:

- какую сборку нужно проверить (Android release / profile, iOS release);
- что именно смотреть (например: холодный старт в светлой и тёмной теме, факт
  сетевого запроса, отрисовка иконки).

## Архитектура

Правила архитектуры — `README.md`, раздел «Правила архитектуры» (feature-first,
направление зависимостей `presentation → domain ← data`, composition root,
`Result<T>`/`AppFailure`, Riverpod, entity vs DTO). Соблюдайте их как есть,
здесь они не дублируются. Нарушение любого из них — блокер.

Дополнительно к README:

- В `lib/core/` кладите код только тогда, когда он действительно используется
  несколькими фичами. Одна фича = код остаётся внутри фичи.
- Исключения data-слоя преобразуются в `AppFailure` внутри репозитория и не
  пересекают его границу.
- Переход DTO → entity — всегда отдельный mapper, не конструктор entity.
- Структура `test/` зеркалит `lib/`. Доменные правила — unit-тестом рядом с
  use case, поведение UI — widget-тестом рядом с виджетом/экраном.

## Нативная часть и ассеты

- При изменении Android-функциональности или `AndroidManifest.xml` сверяйте
  манифест с актуальными потребностями приложения: оставляйте только
  минимально необходимые разрешения и декларации. Разрешения, нужные в
  release-варианте, объявляйте в
  `android/app/src/main/AndroidManifest.xml`; debug/profile-манифесты не
  покрывают Android release. После изменения манифестов проверять нужно именно
  release-вариант Android — запросите эту проверку у пользователя.
- Исходники иконки: `assets/icon/icon_foreground.png` для Android adaptive
  icon и `assets/icon/icon_ios.png` для iOS. Перед регенерацией iOS-версии
  используйте `dart run tool/make_ios_icon.dart`.
- `dart run flutter_launcher_icons` может внести бессмысленное изменение в
  `ios/Runner.xcodeproj/project.pbxproj`: значение
  `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS` не должно
  становиться `AppIcon`; оставьте корректное булево значение (`YES`).
- Настройки холодного старта — в `flutter_native_splash.yaml`. После их
  изменения перегенерируйте нативные артефакты:

  ```sh
  dart run flutter_native_splash:create
  ```

  Затем запросите у пользователя проверку холодного старта в светлой и тёмной
  теме.

## Git

- Перед началом работы смотрите текущую ветку и `git status`; не отменяйте,
  не добавляйте в коммит и не переписывайте чужие изменения.
- Добавляйте в индекс только файлы задачи, перечисляя пути явно. Не
  используйте `git add .`, `git add -A` и `git commit -a`: в рабочем дереве
  есть намеренно неотслеживаемые файлы.
- `docs/` (планы и спеки в `docs/superpowers/`) держите неотслеживаемым. Не
  коммитьте эти файлы без явного запроса пользователя.
- Сообщения коммитов — на английском, в формате Conventional Commits
  (`feat(scope): ...`, `fix: ...`, `chore(ios): ...`). Subject ≤ 50 символов,
  тело — только когда «зачем» не очевидно из subject.
- Не добавляйте в коммит трейлеры об авторстве AI (`Co-Authored-By: Claude`
  и подобные).
- Небольшую изолированную задачу, которую можно завершить за одну рабочую
  сессию, допустимо закоммитить и отправить прямо в `master`, если выполнены
  требуемые проверки.
- Фичу или изменение, которое займёт больше одной рабочей сессии, ведите в
  отдельной ветке и вливайте в `master` только после проверки.
- Перед слиянием убедитесь, что ветка содержит только изменения задачи, и
  выполните релевантные проверки на её итоговом состоянии.
- Не используйте принудительный push, `git reset --hard` или перезапись
  истории без явного запроса пользователя.

## Границы задачи

- Не рефакторьте несвязанный код и не обновляйте зависимости без явной
  причины задачи.
- Не удаляйте и не перезаписывайте пользовательские файлы, фикстуры, планы
  или спецификации без явного запроса.
- Фиксируйте в итоговом сообщении изменённые файлы, принятые компромиссы,
  выполненные проверки и то, что осталось на проверку пользователю.
